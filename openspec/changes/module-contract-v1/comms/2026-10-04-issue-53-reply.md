### What I did with your proposal

Rather than answer the three questions in isolation I wrote up a **module contract** — how
any technology-specific drill set plugs into StudyLoop — and had it reviewed by a four-model
council before replying (the arbitration sits next to it). It is written for you and has
eleven questions, each with a recommended answer, so "yes" or "no, because …" is a complete
reply:

- Proposal: https://github.com/NetDevAutomate/StudyLoop/blob/main/openspec/changes/module-contract-v1/proposal.md
- Implementation plan: `design.md` and `tasks.md` in the same folder.

One paragraph: a module is a directory of **data** — `module.yaml`, drills in StudyLoop's
existing `PracticeDeck` JSON, a `mentor/brief.md`, your `scripts/` — that core validates,
lists under one generic **Labs** entry, and runs through its own runner, consent and mentor.
**Modules declare; core executes.** Nothing a module ships is imported by core.

### Your three questions

1. **Menu mode?** Neither a Kubernetes mode nor "under practice tasks": one generic **Labs**
   entry, hidden until a module is installed, listing drills by module. Otherwise every
   technology becomes a menu item. The entry is StudyLoop's; the content is yours.

2. **Auto Coach and per-deck trust for read-only checks?** Not as a YAML label — "read-only"
   has to be a capability the runner *enforces*, not something a deck declares. In v1 every
   phase (setup / check / cleanup) is consented per execution: the exact argv **and the
   content digest of your script** are shown, confirmed, and re-checked at spawn (R-15
   extended from the command text to the script). The learner triggers each check
   explicitly and the result goes to the Socratic mentor, which decides what to say. There
   is no automatic check after each command in v1. The standing grant Auto Coach needs is
   **v2, together with a view-only credential** (an RBAC `view` ServiceAccount in the
   injected kubeconfig) that makes it defensible — §5.5 says why they ship together.
   Expectation-setting: in the MVP the check runs from the CLI (`studyloop drill check
   <module>/<deck>/<task>`) while the drill itself runs in the web terminal; the browser
   **Check progress** button is v1.1 because it is a new HTTP consent surface.

3. **kind + Docker as an optional extra with doctor checks?** Yes. Prerequisites are an enum
   core owns (`docker`, `kind`, `kubectl` in v1); the probes live in core's `doctor/`, report
   only for installed modules, and never create a cluster or switch context. Default tests
   run with nothing installed; live drills sit behind `STUDYLOOP_LIVE=1` (the `TF_ACC=1`
   pattern).

Your mapping was right on all three seams — decks with `verification.kind: command` plus
`setupCommand`, the existing live console, the mentor as the coaching voice.

### What is live for you as of this comment

The schema half merged in <SHA>: `PracticeDeck` now accepts the six additive fields from
§5.3 — `id` on the deck and on each task, `solution`, `scaffolding` (`guided` / `hinted` /
`unaided` / `exam`, your L0–L3), `mentorNotes`, and `verification.cleanupCommand`. Until
`studyloop module check` lands (the next lane), validate converted decks **from your module
repository**, pointing `uv` at your StudyLoop checkout so its environment is used:

```bash
# run inside the module repo, where decks/*.json live
uv run --project /path/to/your/StudyLoop/checkout python -c 'import sys, pathlib; from studyloop.learning.practice import load_practice_deck; [print(p, "ok:", len(load_practice_deck(pathlib.Path(p)).tasks), "tasks") for p in sys.argv[1:]]' decks/*.json
```

Each deck prints `ok: N tasks` or a Pydantic error naming the field (a glob with no matches is
a zsh error, not a validation failure — it means no `decks/*.json` exist yet). That is the same
Pydantic model MC004 will use, `extra: forbid` included, and it records nothing. The manifest (`module.yaml`, §5.2) can only be drafted against the proposal for
now. Order from here: `module check` / `module add`, then the runner and `studyloop drill`,
then the Labs entry; your live proof against a disposable kind cluster (DoD item 7) is the
acceptance test of the whole standard — if kdrill needs something the contract lacks, either
the need is generic and v1 grows, or kdrill adapts.
