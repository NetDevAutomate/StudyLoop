## Q2

**Q4 (view-only checks).** The recommended answer assumes every CKA/CKAD/CKS check can run under `view`. This is wrong for any drill that verifies Secret contents or reads logs that may contain sensitive data (both are excluded from `view`). Reason: `view` ClusterRole does not grant `get` on Secrets (`kubectl auth can-i get secrets -n ns` returns "no" under `view`). If a drill needs to verify a Secret was created with specific keys, the check script would fail. The credential must be `view` plus a narrowly-scoped role for the specific secret-reading case, or the drill must be redesigned to check only that the Secret exists, not its contents.

## Q3

**W3 (view-only → v2): accept.** The effort estimate is defensible: 4–6 hours for ServiceAccount + RoleBinding + token rotation plumbing, and it only proves correctness on a live cluster. Deferring removes a Kubernetes-specific security surface from v1, and `cleanup` with admin credential already covers the "delete what you created" requirement under C3's consent path.

**W4 (local-path-only add): reject.** Git-url@sha pinning is what makes `modules.lock.json` meaningful for reproducibility. A local-path-only v1 means every reinstall loses the provenance that git sha + digest provide, and contributors cannot share a module without also sharing the git reference. The lockfile becomes a local convenience rather than a reliable replay mechanism. Keep git-url@sha in v1, even if the implementation is a shallow clone + sha verification.

## Q4

**Security holes in §5.5 under C3 and I6:**

1. **Attack: a module script runs `kubectl config use-context` to switch to the learner's current context.** Fix: the runner sets `KUBECONFIG` to a core-controlled temp file and removes `~/.kube/config` from the environment; `kubectl config use-context` fails because the injected kubeconfig has no other contexts.

2. **Attack: a cleanup script deletes resources outside the module's namespace using `kubectl delete all --all -A`.** Fix: the runner creates a per-attempt namespace and sets it as the default in the injected kubeconfig; `cleanup` commands are scoped to that namespace by default, and cross-namespace deletion requires explicit `--namespace` flags the runner can strip or refuse.

3. **Attack: a check script reads `~/.kube/config` directly, bypassing the view-only credential.** Fix: the runner runs in a sandbox with `HOME` set to the per-attempt workdir, not the learner's home; the real `~/.kube/config` is unreachable.

4. **Attack: a module ships a `scripts/setup.sh` that writes to `/etc/hosts` or installs a systemd service.** Fix: the runner drops capabilities (`--cap-drop=ALL` or equivalent) and runs as a non-root user; destructive system-level writes are refused by the container/namespace boundary.

## Q5

**MC013** — Every `scripts/` entry referenced by a drill's `setupCommand`, `command`, or `cleanupCommand` must be executable (`chmod +x`) or explicitly invoked via an interpreter (`bash script.sh`). Symlinks must not point outside the module root.

**MC014** — `target.kind: kubeconfig-context` modules must not reference `kubectl config` commands in any drill; use of `--context`, `--kubeconfig`, or `use-context` is a conformance failure (enforces the runner's context discipline).

**MC015** — `module.yaml` must not declare `capabilities` that no drill in `decks/*.json` uses (e.g., `cleanup` when no `cleanupCommand` exists). Dead capability declarations are a maintenance burden and a misleading signal to reviewers.

## Q8

**Other reviewers will recommend accepting W4 (local-path-only add).** I reject this because git-url@sha pinning is the entire point of a lockfile. Local-path-only means the lockfile records only a directory path and a digest; re-installing on another machine or after the directory is deleted loses provenance entirely. The coordinator's 35–45 hour estimate with W4 assumes contributors will accept a mechanism that cannot survive a reinstall. That is false for any contributor who wants reproducibility. The extra 10 hours for git-url@sha is the correct trade.

## Q9

**The brief's I5 ("how a check result would be delivered to the mentor has not been verified") is accurate, but the proposal does not acknowledge it as a blocker.** The proposal's §5.7 says "the mentor is told the result" without explaining how. The code shows no channel from the runner to the mentor process (`learning/practice.py:verify_practice_task` returns a `PracticeVerificationResult` but does not write to any session-state file the mentor reads). The proposal should mark this as W1 with the same prominence as W3–W6, or the DoD should include a verified delivery path.

**The proposal claims the example deck fails validation today (line 197).** This is correct: the current schema is `extra: forbid` (`schemas.py:52-53`), and the example includes `solution`, `scaffolding`, `mentorNotes`, `cleanupCommand` which are not in the current `PracticeTask` or `PracticeVerification` models. The claim is verified.

**The brief's I3 ("the web UI has no command-execution endpoint today") is correct.** The `web/ws_origin.py` file shows only origin checks; there is no `/api/run` or similar route. The proposal's §5.5 runner contract assumes a web button that triggers command execution, which would be a new, security-critical surface. The proposal does not estimate this work.

---

**Verdict: adopt with changes.** The contract discipline is sound, but §5.5 needs explicit mentor-delivery and web-endpoint scope, W4 should be rejected, and §5.3's example should validate against the current schema before showing additive fields.
