# Council M0 seat: glm-5 (2026-10-04)

## Verdicts

1. **approve both.** Without the PTY loop, `send_input` silently truncates at ~1 KiB (evidence/T/pty-single-write.txt:16-18: 1024-byte write returns 1022) and the envelope never arrives intact. The integration test proves this (integration-pty.red.txt:10-12: envelope reached the mentor as bare keystrokes, not bracketed). The lock prevents learner keystrokes from interleaving with the envelope. Without the ACP lock, a practice_check prompt interleaves with a learner turn (integration-acp-no-overlap.red.txt:10-12: 1 overlapping session/prompt). The lock gives strict FIFO, no signature change, and is the only way to honor S4.

2. **amend: local hop (b), but add explicit mitigations.** The security consequences of (b): the route accepts a text injection into the mentor's terminal. If unauthenticated, any local user can inject. If authenticated but unvalidated, a compromised CLI can send arbitrary text. Mitigations: loopback-only (the server already binds 127.0.0.1 by default), authenticated (existing session auth), server-side rendering (never trust the CLI's rendering), size bound (8 KiB per the ADR), rate limit (one envelope per phase completion, enforced at the route). The route is owned by W (wave 2). The MVP ships with (a) `no_active_session` for CLI runs, which is honest but makes the contract item unexercisable outside tests; (b) should be implemented in wave 1 so CLI drills can deliver.

3. **amend: track DEC 2004 in the transport and fall back; confirm the probe is an owner task, not a gate.** PTYTransport currently has no visibility into whether the child enabled bracketed paste. Tracking `ESC[?2004h/l` in the child's output (as xterm does) lets the transport fall back to bare text + CR when off. Fallback failure mode: the envelope arrives as separate lines, the first one bare. The probe that starts each harness agent and looks for the enable sequence is an owner-run task before wave 1, not a gate — the transport must work without it.

4. **approve auto-submit with documented hazard.** The trailing CR submits whatever is on the input line. If the learner has a half-typed draft, the draft is submitted together with the envelope. This is rare (the learner triggered the check seconds earlier) and is the price of not needing editor state. The alternative ("hold until the input line is empty") is not implementable without that state. The hazard is documented in the contract, not in the UI.

5. **amend: 120 s bound, report, no retry, but note the missing constant.** acp.py:60-62 defines handshake timeouts; there is no constant bounding a prompt turn (UNVERIFIED: I did not read every line of acp.py to confirm absence). A 120 s bound is reasonable by analogy to _SESSION_NEW_TIMEOUT_S = 60.0 (acp.py:58). No retry because S4 forbids duplicate envelopes. If the prompt times out, the envelope is lost and the learner sees `timed_out`.

6. **amend: the spec delta's three failure reasons are correct; the ADR is right that two are unreachable by construction under the chosen design.** "Transport closed" maps to `transport_closed`. "Size exceeded" cannot happen because the renderer truncates to 8 KiB before sending; the header is bounded by slug validation (MC014) and enum values, so no envelope is too large. "Serialisation refused" cannot happen because Q2 queues behind the in-flight turn; the nearest failure is a prompt that never ends, which is `timed_out`. The spec should keep the three reasons and add a note that two are unreachable under ADR-0012's design, so future readers understand why they are not tested for.

7. **The ADR gets two things wrong.** (1) F1 claims `send_input` "returns None regardless of the byte count written" (ADR line ~15). pty.py:351-360 shows it returns `None` implicitly (no return statement) after discarding the return value of `os.write`, which is not the same as "returns None" — it returns nothing, which is `None`, but the phrasing obscures that the return value is discarded, not checked. The evidence (pty-single-write.txt:16-18) shows the write returns 1022, but the code never sees it. (2) The ADR says "the web terminal already relies on this [bracketed paste] for learner pastes" (ADR line ~70). UNVERIFIED: I did not read the vendored xterm source to confirm `bracketedPasteMode` tracking. The brief says the vendored xterm tracks it, but I did not verify this against the actual vendored code.

The two claims I expect other seats to accept too readily:
- F5: "The learner's browser already pastes through DEC mode 2004 brackets (vendored xterm tracks `bracketedPasteMode`)" — I did not verify the vendored source, and neither will most seats.
- "The web terminal already relies on this for learner pastes" — same; it sounds authoritative but the code was not read in this spike.

## Findings: 3 raised

1. `send_input` does not "return None" — it discards the return value of `os.write` and returns implicitly (pty.py:356). The distinction matters for whether a caller could ever check the count.
2. The ADR claims the vendored xterm tracks `bracketedPasteMode` (F5) but does not cite a file:line. I did not verify this against the vendored source.
3. The ADR says "the web terminal already relies on this for learner pastes" (line ~70) without a file:line for the xterm implementation. The brief repeats the claim; I did not verify it.
