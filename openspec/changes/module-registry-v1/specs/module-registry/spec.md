## Purpose

Provide a reviewed, versioned catalogue of optional StudyLoop modules
without executing author content or coupling core study to a service.
These are proposed phase-1 requirements, not current product claims.
The planned implementation lives in the separate registry repository;
see design.md for layout and verified existing dependency paths.

## ADDED Requirements

### Requirement: Registry entries identify a publisher and immutable release

The registry SHALL validate release and publisher records against the
versioned field contract in design.md. A release SHALL have a unique
qualified coordinate and canonical version. A published release's source,
artifact, checksum, compatibility and capabilities SHALL NOT be rewritten.

#### Scenario: An author submits a valid new release
- **WHEN** a release has verified publisher ownership, valid fields and
  a previously unused coordinate/version
- **THEN** offline validation accepts its structure for further review
- **AND** acceptance alone neither publishes nor installs it

#### Scenario: A release identity is reused with different content
- **WHEN** an entry changes the digest or permissions of a published version
- **THEN** validation rejects it with an immutable-release diagnostic
- **AND** requires a new version rather than overwriting history

#### Scenario: A malformed or ambiguous version is submitted
- **WHEN** an entry has an unknown field/schema, duplicate coordinate,
  invalid SemVer or malformed application version constraint
- **THEN** validation rejects the field with a stable diagnostic

### Requirement: Registry review binds artifact bytes to the pinned source

Review SHALL verify repository and asset identities, full source commit,
archive-byte SHA-256, byte limits and content equality using the
sha256-tree-v1 algorithm defined in design.md. Branches, tags and short
SHAs SHALL NOT substitute for a source pin.

#### Scenario: An archive and source agree
- **WHEN** trusted validation reads the pinned source subtree and archive
- **THEN** their normalized content digests agree before approval
- **AND** conformance evidence names those exact bytes and checker version

#### Scenario: An asset is replaced or a repository changes identity
- **WHEN** fetched bytes or numeric repository/asset IDs differ
- **THEN** validation rejects the release without changing existing metadata

### Requirement: Validation inspects bounded data and never executes modules

Registry validation SHALL enforce the archive, path, network and resource
limits in design.md. It SHALL NOT import modules, run their tests/scripts,
execute package hooks or accept their workflows as trusted validation.
The default validation/test lane SHALL require no network or credentials.

#### Scenario: A hostile archive attempts traversal or resource exhaustion
- **WHEN** input contains links, traversal, duplicate/colliding paths,
  special files or exceeds streamed resource limits
- **THEN** validation stops with an unsafe-archive diagnostic
- **AND** no file is written outside test-owned temporary storage

#### Scenario: A submitted script would write a marker file
- **WHEN** the candidate passes through validation and catalogue generation
- **THEN** the script is treated only as bytes
- **AND** its marker file is never created

#### Scenario: A download redirects to a private address
- **WHEN** bounded online verification receives a disallowed redirect
- **THEN** it refuses the request without accessing that destination
- **AND** no credentials are forwarded to another origin

### Requirement: Only reviewed trusted publication produces catalogue snapshots

The catalogue SHALL be generated deterministically with explicit release
inputs and published only from the approved protected branch. Publication
SHALL revalidate the merged records using trusted code. Untrusted PR jobs
SHALL receive no write/deploy credentials or privileged execution path.

#### Scenario: Two builds use the same records and publication inputs
- **WHEN** catalogue generation runs twice in clean environments
- **THEN** the generated bytes and checksum are identical

#### Scenario: A submission edits its own validator or workflow
- **WHEN** a module-entry PR also changes trusted execution logic
- **THEN** automated entry approval is refused and a separate tooling
  review is required
- **AND** PR-head workflow code is not run with privileged credentials

#### Scenario: Concurrent accepted PRs conflict after merging
- **WHEN** merged records create a duplicate or immutable-release violation
- **THEN** publication refuses that snapshot despite earlier PR checks

### Requirement: Lifecycle changes preserve release history and deny unsafe selection

The registry SHALL enforce the lifecycle transition table in design.md.
Candidates SHALL remain unpublished. Yanked and revoked versions SHALL
remain as tombstones, not selectable new releases. Revocation SHALL be
terminal; records SHALL carry reviewed reasons and transition history.

#### Scenario: A maintainer withdraws an active version
- **WHEN** a reviewed transition yanks that version
- **THEN** the next higher-sequence catalogue retains its identity/history
- **AND** marks it unavailable for new selection

#### Scenario: A revoked version is reactivated or silently removed
- **WHEN** a candidate snapshot reactivates it or omits its tombstone
- **THEN** publication rejects the snapshot

### Requirement: Namespace changes and emergencies follow accountable governance

The registry SHALL verify publisher ownership independently of submitted
names, retain namespace identity across login changes, and apply the
review/transfer/emergency policy in design.md. It SHALL NOT recycle an
abandoned namespace or expose private security reports in public records.

#### Scenario: An unrelated author claims an existing namespace
- **WHEN** the author lacks verified authority for that publisher
- **THEN** the claim is refused even if schema validation passes

#### Scenario: A responder revokes an unsafe release urgently
- **WHEN** the designated responder uses the documented emergency path
- **THEN** revocation and the exception are recorded
- **AND** independent follow-up review is due within two working days
- **AND** that exception cannot activate or expand a release

### Requirement: Compatibility and review evidence are explicit and non-executable

Every accepted entry SHALL name supported module contract, application
constraint, prerequisites, capabilities, license and pinned conformance
evidence matching its manifest. Descriptions SHALL be bounded plain text.
Review SHALL NOT imply a sandbox, mastery, command approval or certification.

#### Scenario: The module requests more capabilities than its entry reports
- **WHEN** trusted validation compares the manifest with registry metadata
- **THEN** it rejects the mismatch rather than hide the extra permission

#### Scenario: An entry claims an unimplemented checker contract
- **WHEN** no trusted released checker supports the claimed module contract
- **THEN** it may remain a labelled development fixture but cannot publish

### Requirement: The registry ships with reproducible contributor and operator checks

Phase 1 SHALL provide offline validation, deterministic build, typed
diagnostics, good/bad fixtures, submission/update/withdrawal templates,
governance and a publication/recovery runbook. Real publication SHALL
require the readiness gates in tasks.md, not merely scaffolded files.

#### Scenario: A newcomer follows the repository's development instructions
- **WHEN** they run checks in a clean supported environment with network
  denied after dependency installation
- **THEN** valid fixtures pass and every required rejection case fails
  diagnostically without Docker, kind, model access or learner data

#### Scenario: The registry has fixtures but no real compatible modules
- **WHEN** phase-1 tooling passes
- **THEN** it is reported as tooling-ready, not a publicly usable module
  ecosystem or a completed phase-2 consumer
