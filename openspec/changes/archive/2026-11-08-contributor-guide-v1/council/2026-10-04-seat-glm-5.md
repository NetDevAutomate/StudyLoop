## 2. Naming standard

### Branch names

Already settled in `docs/contributing.md:175-177`:
- `feat/…` — new capability
- `fix/…` — bug fix
- `docs/…` — documentation only
- `test/…` — test-only change
- `lane/…` — reserved for maintainer remediation lanes (K5)

### Commit subjects

Pattern from last 300 commits (`git log --format=%s`):
```
<type>(<scope>): <imperative description>
```

**Types observed:** `docs` (106), `test` (91), `fix` (49), `feat` (37), `chore` (6), `ci` (1)

**Scopes observed:** `now`, `web`, `openspec`, `plan`, `mcp`, `agents`, `session`, `doctor`, `learning-tier`, `verify`, `spec`

**Rule:** Scope is **open** (any module/service name). Use the nearest owning module. When a change spans multiple scopes, pick the primary affected one.

**Examples from real history:**

| Commit SHA | Commit subject | Notes |
|------------|----------------|-------|
| `fa5d76be` | `feat(now): the body double proposes one tiny, passive first move (#30)` | Feature with issue reference |
| `653e825b` | `fix(web): give the voice health probe a budget a healthy host fits in` | Bug fix with context |
| `a69867bf` | `test(plan): RED — husk discovery and plan repair <id> (item 3, D-C)` | Test-first commit with marker |
| `71c09393` | `docs: contributor code map, testing cookbook and optional-modules proposal` | Docs without scope (repository-wide) |
| `96806feb` | `chore(release): date the 0.5.0 CHANGELOG heading for the 2026-09-21 cut` | Release chore |
| `fb63fb6b` | `fix(doctor): read kiro-cli's verdicts where kiro-cli actually writes them` | Bug fix with precise scope |

**Scope decision:** `docs(openspec)` vs `docs(contributing)` — use the module or section being documented. `docs(openspec)` for OpenSpec changes; `docs(contributing)` for contributor guide changes; plain `docs:` for site-wide or cross-cutting docs.

### PR titles

**Standard:** Same as commit subject, prefixed with conventional-commit type and scope.

**Rule:** The PR title becomes the merge commit subject. Maintainers merge with a merge commit (K5), so the PR title must follow the commit-subject standard.

**Examples from merge commits:**

| PR | Merge commit subject | PR title (inferred) |
|----|---------------------|---------------------|
| #41 | `Merge PR #41 (feat/learning-tier-fed): item 1, the mentor writes (S1-0 through council review 9)` | `feat(learning-tier): item 1, the mentor writes (S1-0 through council review 9)` |
| #42 | `Merge PR #42 (fix/coverage-gate-selftest-timeout): coverage-gate self-test carries its own timeout` | `fix(coverage-gate): coverage-gate self-test carries its own timeout` |
| #40 | `Merge PR #40 (fix/ws-drained-pull-future): read a done pull future on every WS pump exit` | `fix(ws): read a done pull future on every WS pump exit` |

### PR description requirements

Must answer five questions (contributing.md:219-226):
1. What learner or contributor problem does this solve?
2. What changed?
3. Which automated checks passed, and where?
4. Which live or manual journey did you check yourself?
5. What remains unverified?

### PR-to-changelog mapping

Each PR that changes user-visible behaviour adds one `[Unreleased]` entry under the appropriate section:
- `### Added` — new capability
- `### Changed` — modified behaviour
- `### Fixed` — bug fix
- `### Removed` — deprecated feature removed
- `### Security` — security fix

The entry is written in learner terms, not code terms (contributing.md:197-201).

## 3. Changelog process

**Who writes:** The contributor, in the same PR that makes the change.

**When:** Before requesting review, as part of the PR.

**Which section:** See Q2 (PR-to-changelog mapping).

**How `release-consistency` is satisfied:** `just release-consistency` runs `scripts/check-release-consistency.py`, which validates:
1. `CHANGELOG.md` has an `[Unreleased]` section
2. Version numbers in `pyproject.toml` files agree
3. (With `--release`) the git tag exists and changelog date matches

**Example diff:**

```diff
--- a/CHANGELOG.md
+++ b/CHANGELOG.md
@@ -8,6 +8,10 @@ StudyLoop is preparing its first pre-release. The public API and installation
 experience may change before `1.0.0`.

 ### Added
+
+- A new `studyloop topic` command logs activity without starting a session.
+  Use it from agent prompts that track study but do not drive a mentor.
+
 - A first-contribution walkthrough, source-code map and testing cookbook with runnable Python
   and Playwright examples. An optional-topic-module proposal explains the boundaries for
   Kubernetes drills and a possible registry; no plugin runtime or registry is introduced.
```

## 4. Module index page outline

1. First paragraph states: "This is a design proposal. The module registry and lifecycle do not exist yet."
2. Links `openspec/changes/module-contract-v1/proposal.md` §9 as the contract definition.
3. Describes the goal: topic-specific practice (e.g., Kubernetes drills) without topic-specific core dependencies.
4. Lists what exists today: JSON practice decks, `verification.kind: command`, manual consent per check.
5. Explains what does NOT exist: automatic setup/teardown, registry loader, plugin installation, immutable artifact store.
6. Names the safety boundaries: per-command consent, no automatic execution from YAML fields, read-only label does not establish safety.
7. Describes the staged approach: agree contract → prove vertical slice → prove boundary with second topic → publish manifest → consider installation.
8. Provides a proposal template for would-be authors.
9. Explicitly warns: "Do not add a `modules:` section to your config expecting it to work."
10. Links to contributor-testing.md for test patterns and contributing.md for review process.
11. States the first useful slice is done when a new contributor can run one drill, consent to one check, and cancel safely.
12. References the testing cookbook for deterministic tests that must work without Docker, kind, or cloud credentials.

**Must not promise:** A working registry, automatic module installation, that any module contract field is final, or that a manifest format is stable.

## 5. Truthfulness mechanism

### Drift-test patterns to add

1. **CLI command resolution** (already in `test_docs_drift.py:343-358`): Every `studyloop ...` example in fenced code blocks resolves against the real Click tree.
   - Add similar tests for new pages' CLI examples.

2. **Heading presence tests**: Each new page has a test that asserts key headings exist.
   - Example: `test_contributor_modules_has_design_stage_heading()` asserts first paragraph contains "design proposal".

3. **Link validity**: `test_docs_drift.py` already checks links resolve (lines 331-340).
   - Extend to cross-page links between new contributor pages.

4. **Command execution verification**: For pages showing shell commands, add tests that run the command and assert output matches documentation.
   - Example: `test_contributor_testing_examples_run()` runs `just test --help` and asserts output contains documented flags.

### How a writer proves "I ran it"

1. Every CLI command in the page is validated by the drift test suite (CI fails if command does not exist or flag is wrong).
2. Every code snippet is either:
   - A test fixture that exists in the test suite (with file path reference), OR
   - An inline command validated by a drift test.
3. PR must include the drift test alongside the page.
4. CI green proves the commands run; the writer signs off in the PR description.
