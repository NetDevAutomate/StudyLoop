# StudyLoop Struggle-Extraction Pipeline — Fresh-Session Handoff

**Created**: 2026-05-31 · **For**: a fresh session to build the struggle-extraction pipeline to completion via fanout subagents with binary, data-driven pass/fail gates.


---

## Executive summary

Goal: build an automated pipeline that reads AI study session transcripts from sessions.db, identifies topics the learner struggled with, writes structured rows to study_progress, and surfaces them in the Generate panel's topic dropdown — without ongoing human intervention after a single upfront labeling session.

Architecture chosen: export-then-extract with dual trigger. On-export trigger (existing Stop hooks) calls a new `studyloop extract-struggles --incremental` CLI subcommand immediately after each session is written to the DB. A second periodic trigger (cron or manual) runs `studyloop extract-struggles --full` to reconcile all kiro_cli sessions that have no study_progress rows yet. The extractor is an LLM call (Anthropic-compat, forced tool_use, temperature=0) that produces structured {topic, concept, confidence} triples written via the existing record_progress() upsert path.

WHY this architecture over alternatives: record_progress() already exists, is tested, and uses uuid5 keying that makes re-running idempotent. The forced tool_use JSON extraction pattern is already implemented in AnthropicCompatGenerator (anthropic_compat.py) — the extractor reuses it verbatim. Dual trigger (incremental + reconcile) means the dropdown is always fresh without expensive full-DB scans on every session close.

Biggest risk: the ground-truth problem. The 'fully automated, remove the human' framing is partially false. The eval loop needs at least one human labeling session (~30 minutes) before it can measure anything honest. The workflow neutralizes this by making the human gate a one-time upfront act, not an ongoing requirement, and by making the pipeline plumbing completely independent of the quality eval — the system ships useful behavior before the eval loop ever runs.

## Architecture decision

ARCHITECTURE: Export → Pre-filter → Extract → Upsert, with dual trigger.

Pipeline contract (left-to-right):
1. session-export writes raw messages to sessions.db (already committed, tested).
2. Pre-filter: skip sessions where source != 'kiro_cli' AND source is not in a known study project list. Skip any session where >50% of messages have role='tool_use' or role='tool_result' (claude_code subagent noise). This is deterministic Python, not LLM work.
3. Extractor: called for each qualifying session_id. Takes (session_id, messages: list[{role, content}]) and returns list[ExtractorResult(topic, concept, confidence, notes)]. The stub extractor returns a hardcoded fixture. The LLM extractor calls POST /v1/messages via the existing httpx pattern from AnthropicCompatGenerator with a forced emit_struggle_extractions tool_choice and temperature=0.
4. Upsert: for each ExtractorResult, call record_progress(topic, concept, confidence, notes). The uuid5 keying makes this idempotent on re-runs.
5. The web UI's GET /api/history/struggling-topics route reads the result via get_struggling_topics() — no change needed there.

WHY the dual-trigger approach:
- Incremental trigger (Stop hook, per-session): keeps the dropdown fresh at zero user effort. Runs the extractor only on the session just exported (O(1) LLM calls per session close). Wired as a second Stop hook in agents/claude/settings.json and equivalent entries for Kiro/Gemini/OpenCode.
- Periodic full-reconcile (`studyloop extract-struggles --full`): backfills the 395 existing kiro_cli sessions that have never been processed. Run once manually, then optionally scheduled. Guarded by a budget cap.

WHY NOT inline into the export hook as a single bash script: the extractor needs Python for the LiteLLM/Anthropic call, pre-filter logic, and idempotent upsert. Bash cannot do this cleanly.

WHY the LLM extractor is a SEPARATE module from classifier.py: classifier.py is a deterministic keyword/regex session-type tagger (writes session_type to sessions table). The extractor infers learning content from message semantics (writes to study_progress). They solve different problems, share only the DB connection pattern, and must not share test fixtures.

Red-team incorporation: the red-team's core insight — that autoagent's 100%-pass target and prose-output assertions are architectural mistakes — is absorbed wholesale. The handoff separates pipeline correctness (100%-passable, stub-based, deterministic) from quality measurement (F1-based, held-out golden set, not 100%). The loop targets precision>=0.70 / recall>=0.60 on a held-out human-labeled set, not 100% pass.

## Critical flaws and how this plan resolves them


### ⚠️ Ground-truth circularity: if the eval labels are generated by the same LLM being evaluated, the loop optimises for the judge's blind spots, not correctness.

**Resolution:** One-time human labeling pass. A human reads exactly 8 high-quality kiro_cli study sessions (listed in Phase P2) from the live sessions.db, produces a JSON fixture at packages/studyloop/tests/fixtures/eval_golden.json with schema [{session_id, expected_topics: [{topic, concept, confidence}], notes}]. This file is the permanent, frozen ground truth. LLM is never the label source. The human is in the loop once, not removed.

### ⚠️ '100% pass' target for NLP extraction is either trivially gamed, impossible, or a sign of overfitting.

**Resolution:** Two-tier gate structure. PIPELINE tests (stub extractor, deterministic) genuinely target 100% pass — they test plumbing only (does record_progress get called with valid schema fields?). QUALITY eval (LLM extractor, golden set) targets precision>=0.70 AND recall>=0.60 AND false_positive_rate_on_build_sessions==0. These thresholds are set before the loop runs and are not adjusted during it.

### ⚠️ autoagent Goodhart trap: hill-climbing the benchmark without a held-out split means the meta-agent learns the fingerprint of the training tasks, not the capability.

**Resolution:** Split eval_golden.json 5/3 before the first loop run (5 train, 3 held-out). Loop optimises on train. Held-out score is reported every 5 iterations but NEVER drives the keep/discard signal. If F1_train - F1_held_out > 0.10 for two consecutive held-out checks, the loop halts and flags overfitting. The held-out split files are committed as a separate fixtures file and are never shown to the prompt-improvement meta-agent.

### ⚠️ LLM non-determinism makes binary pass/fail gates flaky even at temperature=0.

**Resolution:** Three concrete rules: (1) temperature=0 on ALL extractor LLM calls. (2) Pipeline tests NEVER assert on the string content of LLM output — only on structural validity: topic is a non-empty string after strip/lower, concept is non-empty, confidence is one of {struggling, learning, confident}. (3) Quality eval computes Topic Jaccard on a canonical vocabulary (topic_vocab.json) after normalization, not raw string equality. Loop keep/discard uses mean F1 over 2 eval runs per candidate prompt.

### ⚠️ Unattended LLM eval loop with no cost guardrails can issue thousands of API calls against 1940 sessions.

**Resolution:** Three hard stops in the loop runner: MAX_ITERATIONS=20, BUDGET_USD_PER_RUN=2.00 (tracked via LiteLLM gateway at localhost:4040 token counts × model price), BUDGET_USD_TOTAL=5.00 cumulative. Eval batch is capped at 50 training sessions per iteration (stratified sample from the 5 training sessions, oversampled for diversity). Use haiku for all meta-agent mutation iterations; only run the final accepted prompt on sonnet to confirm quality holds.

### ⚠️ Playwright tests cannot assert correct agent prose output — mixing UI assertions with LLM output correctness assertions creates a fragile, non-reproducible test.

**Resolution:** Clean boundary enforced. Playwright tests assert ONLY: (a) given known DB state (seeded fixture or route stub), the dropdown renders the correct option values; (b) the API returns the correct schema shape. Extractor correctness is tested in a separate pytest tier (packages/studyloop/tests/test_extractor_quality.py) using the golden fixture. These two tiers share no code and have separate pass/fail criteria.

### ⚠️ The log_topic MCP tool and CodexExporter are uncommitted in locked worktrees — they branch from stale origin/main (SHA 0fe6533 is older than the 8 commits now on main at 81b32a9).

**Resolution:** The fresh session must cherry-pick both worktrees' uncommitted changes onto a feature branch from current main before any other work begins. This is Phase P0 and blocks everything else. Specific files: worktree agent-a5c6cbcc5d4678224 has mcp/tools.py (modified) + test_mcp_log_topic.py (untracked); worktree agent-ab543b6e53cb428a0 has export_sessions.py (modified) + exporters/__init__.py (modified) + exporters/codex.py (untracked) + test_codex_exporter.py (untracked).

### ⚠️ Interactive agent commands (Claude /slash, Kiro @skill, Gemini @agent) cannot be invoked headlessly in a test runner — 'testing the command' requires a live interactive session.

**Resolution:** Test the extractor CORE function directly with pytest (pure Python, no agent). The per-harness command is a thin wrapper calling `studyloop extract-struggles` CLI. Its existence is asserted by two lightweight smoke tests: (1) CliRunner invocation of `studyloop extract-struggles --help` exits 0 (CLI wiring); (2) file-presence assertion that the per-harness hook/skill files contain the expected CLI command string. No interactive agent spawn needed.

- kiro_52edd73b (ZTM data engineering)
- kiro_53f8d4bb (SageMaker Workshop)
- kiro_34d44273 (AWS Obsidian notes)
- kiro_c88f4eef (graphrag session)
- kiro_33b5a7ed (arjancodes classes/dataclasses)
- kiro_0b7a9687 (arjancodes type_hints)
Plus 3-5 NEGATIVE sessions (pure build sessions with source=claude_code that must produce ZERO struggle rows — include these to test false-positive rate).

Output: packages/studyloop/tests/fixtures/eval_golden.json with schema:
[{session_id: str, expected_topics: [{topic: str, concept: str, confidence: str}], is_negative: bool, notes: str}]

CANONICAL VOCABULARY (prevents string-match flakiness):
Create packages/studyloop/src/studyloop/extractors/topic_vocab.json seeded from known sessions. The LLM extractor prompt instructs output using only canonical keys. Jaccard similarity is computed on the canonical key set after normalization (lowercase, strip punctuation). This makes the eval stable across minor prompt variations.

SPLIT (before first loop run, immutable after):
5 sessions in train split, 3 sessions in held-out split. File: packages/studyloop/tests/fixtures/eval_split.json. This file is committed once and never modified by the loop.

METRICS (computed by pure Python, not LLM-judged):
- Topic Jaccard: |predicted ∩ expected| / |predicted ∪ expected| on normalized canonical topics. Gate: Jaccard >= 0.50 on held-out.
- Confidence precision: of all (topic, confidence=struggling) pairs predicted, what fraction match a human-labeled struggling row. Gate: precision >= 0.70.
- False positive rate on negative sessions: number of study_progress rows written for sessions marked is_negative=true must equal 0. Binary, non-negotiable.

All three gates must pass for the quality eval tier to be marked green. These are measured on the held-out split only for final reporting; the loop uses train-split scores for keep/discard.

## Human-in-the-loop reality

GENUINELY AUTOMATABLE (no human after initial setup):
- Pipeline plumbing (P1): 100% automatable. Stub extractor, deterministic, binary pass/fail.
- Per-harness hook wiring (P5): automatable write + file-content assertion.
- Playwright UX tests (P3): automatable with seeded fixtures.
- LLM extractor baseline eval (P4): automatable after golden labels exist. Cost is pre-approved by the budget cap.
- autoagent improvement loop (P6): automatable within budget/iteration caps. Runs unattended.
- Periodic backfill reconcile: automatable via cron or manual trigger with --full flag.
- Incremental extraction on session close: fully automated via Stop hooks after P5.

HUMAN GATE IS UNAVOIDABLE — exactly two places:

1. GOLDEN LABEL CURATION (P2, ~30 minutes, done once): A human must read 8-11 real sessions and decide which topics the learner actually struggled with. This cannot be automated because: (a) LLM-generated labels make the eval circular; (b) the 'struggled' definition requires human judgment about conversational context. The human reads user message turns, decides topic/concept/confidence, writes eval_golden.json. After this single session, the human is genuinely out of the loop for all subsequent runs. The fixture is committed and immutable — the loop never modifies it.

2. LIVE API SPEND APPROVAL (P4/P6, one-time): The first run against the live API (eval_runner.py calling Anthropic/Bedrock endpoints) should be reviewed before it runs to confirm the budget cap is acceptable. This is not a continuous gate — it is a one-time 'yes, I accept the 5.00 USD budget for this loop' confirmation. After that, the loop runs within the cap autonomously.

3. PRODUCTION DB WRITE SIGN-OFF (P7, ~5 minutes): The human runs `studyloop extract-struggles --full --dry-run --limit 10` and confirms the output looks sane before running `--commit`. This is a quality spot-check, not an approval gate on every extraction. It is required once for the initial backfill; subsequent incremental extractions run unattended.

WHAT DOES NOT REQUIRE A HUMAN AFTER INITIAL SETUP:
- Running the improvement loop again when new sessions accumulate (automated, budget-capped).
- Incremental extraction on each new study session (fully automated via hooks).
- The Playwright and pipeline test suites (fully automated in CI).
- Adding new sessions to the golden set (semi-automated: run eval_runner with --suggest-labels to get LLM candidate labels, human spot-checks only the uncertain ones — but this is optional quality improvement, not required for the pipeline to function).

HONEST BOTTOM LINE: the user's goal of 'remove the human from the loop' is achievable for the ongoing operation of the system. It is NOT achievable for the initial calibration. The human does 45 minutes of work once, then the system runs fully autonomously within budget caps forever after.

## autoagent-derivative hill-climb loop

The derivative does NOT import autoagent wholesale. It is ~200 lines of pure Python in packages/studyloop/extractors/improve_extractor.py, pattern-matching autoagent's architecture at the concept level.

EDITABLE SURFACE (mirrors autoagent's SYSTEM_PROMPT + create_tools()):
- EXTRACTOR_PROMPT: the system+user prompt string sent to the LLM to identify struggles from raw messages
- post_process(raw_json: dict) -> list[ExtractorResult]: normalizes the LLM's tool-use JSON output into ExtractorResult triples

FIXED BOUNDARY (not mutated by the loop):
- eval_runner.py: the score function
- record_progress(): the DB write path (used only for final production run, not during loop)
- results.tsv: the experiment ledger
- eval_golden.json + eval_split.json: the frozen ground truth

LOOP ALGORITHM (implement as improve_extractor.py):
0. Load current best prompt from extractor_candidate.py (or use INITIAL_PROMPT if first run). Run eval on train split. Record baseline row in results.tsv: prompt_hash=sha256(prompt)[:8], F1_train, precision_train, recall_train, F1_held_out='', cost_usd, status='baseline', mutation_description='initial'.
1. Collect false-negatives (golden labels the extractor missed) and false-positives (extractor output not in golden labels) — up to 5 examples each, shown as (session_excerpt: first 200 chars of user messages, expected, got).
2. Call meta-agent (haiku, temperature=0.7) with mutation prompt containing: current EXTRACTOR_PROMPT, current F1_train score, FN examples with label 'these are struggles you missed', FP examples with label 'these are non-struggles you hallucinated', instruction 'mutate the prompt to fix these failure modes', simplicity criterion 'if F1 is equal, prefer the shorter prompt'.
3. Extract the mutated EXTRACTOR_PROMPT from the meta-agent's response (expect it between ```prompt ... ``` fences).
4. Run eval on train split with the mutated prompt (temperature=0 for extractor, n=2 passes, use mean F1).
5. Keep if mean_F1_train improved. Keep if equal and prompt length decreased. Discard otherwise. Record in results.tsv with status='keep' or 'discard'.
6. Every 5 iterations: run eval on held-out split with current best prompt. Record F1_held_out in results.tsv. If F1_train - F1_held_out > 0.10 for 2 consecutive held-out checks, set status='overfit_gate' and stop.
7. Budget checks (before each iteration): if iterations >= MAX_ITERATIONS (20) or cumulative_cost_usd >= BUDGET_USD_TOTAL (5.00), set status='budget_stop', emit summary, stop.
8. On stop (any reason): write extractor_candidate.py with best EXTRACTOR_PROMPT + post_process() + run_extraction(session_id, db_path) function.

BASELINE-FIRST DISCIPLINE:
The loop MUST run the baseline before any mutation. The baseline row in results.tsv is the reference point. A mutation is only 'better' relative to the baseline, not relative to an arbitrary starting point.

TEMPERATURE ASYMMETRY (intentional):
- Extractor LLM call: temperature=0 (deterministic extraction, stable eval signal)
- Meta-agent mutation call: temperature=0.7 (diverse mutation strategies, escape local optima)

COST TRACKING via LiteLLM gateway:
The gateway at localhost:4040 returns usage.input_tokens + usage.output_tokens in each response. Compute cost as (input_tokens * price_per_input_token + output_tokens * price_per_output_token) for the model used. Haiku pricing: ~$0.00025/1K input, ~$0.00125/1K output. A 5-session eval run costs approximately $0.05-0.15. 20 iterations costs approximately $1.00-3.00 — well within the 5.00 USD budget.

## Appendix — red-team risk register (from analysis)


### Angle: Red-team of the proposed "data-driven, remove-the-human, loop-until-100%-pass" architecture for LLM-based struggle extraction in StudyLoop

- **[blocker] Ground-truth circularity: if labels for the test set are generated by an LLM, grading the extractor with those same labels means you are using an LLM to validate an LLM on the same data it was prompted with.**
  - Why: The loop will converge on prompts that please the judge, not prompts that correctly identify real struggles. A student who genuinely struggled with 'outer joins' but phrased it conversationally ('this is confusing') will never appear in the labeled set if the judge LLM also fails to tag it. The loop optimises for the judge's blind spots, not correctness.
  - Mitigation: One-time human labelling pass on ~50-100 real sessions from sessions.db — read the raw messages, manually decide topic/concept/confidence='struggling'. This is the ONLY place the human must stay in the loop. Store as a fixtures/ JSON file. All subsequent loop iterations are measured against this fixed, human-authored holdout. The human is in the loop once, not removed.
- **[blocker] '100% pass' as a target for a subjective NLP extraction task is either impossible, trivially gamed, or a sign of overfitting.**
  - Why: Struggle detection is inherently ambiguous: 'this is hard' is a struggle signal; 'error: undefined variable' in a debugging session is not. A 100% gate on a ~50-sample labeled set means you've written tests loose enough that everything passes (trivial), or you've tuned the prompt so hard to the labeled set that it fails on unseen sessions (overfit). Precision/recall on a held-out set is the honest metric.
  - Mitigation: Set explicit thresholds: precision >= 0.80 (don't flood the UI with false struggles), recall >= 0.70 (don't miss real struggles), measured on a 20% held-out slice of the hand-labeled set. The autoagent loop targets these thresholds, not 100%. Emit a confusion matrix on each run.
- **[major] autoagent's Goodhart trap: hill-climbing on the benchmark task set with no held-out split means the meta-agent will eventually find prompt/tool changes that overfit to those specific tasks.**
  - Why: program.md's overfitting guard (line 197) is a prose heuristic enforced by the same LLM doing the hill-climbing — it will rationalise borderline task-specific hacks as 'general improvements'. The keep/discard rule (program.md:160-165) is purely score-delta-based on the same task set; there is no separate validation set. Over many iterations, the harness learns the fingerprint of the tasks, not the capability.
  - Mitigation: Split the labeled session corpus into train (80%) / held-out (20%) before any loop starts. The loop optimises on train. Held-out score is reported but NEVER used as the keep/discard signal — it is the honest accuracy estimate. Periodically (every 5-10 iterations) run against held-out as a sanity check. If train and held-out scores diverge, stop the loop and flag overfitting.
- **[major] Non-determinism of LLM extractors makes binary pass/fail gates flaky. An extractor run at temperature > 0 can return 'outer joins' on one invocation and 'sql joins' on the next.**
  - Why: The test suite will have intermittent failures that are not bugs in the extractor — they are sampling variance. A loop that treats these as real failures will thrash: discard a good change because of noise, keep a bad change that happened to get lucky. autoagent already has no temperature setting in agent.py; if the extractor also lacks one, variance compounds across meta-agent AND extractor.
  - Mitigation: Three concrete gates: (1) Force temperature=0 on the extractor LLM call. (2) Assert on STRUCTURED fields only — topic is a non-empty string, concept is a non-empty string, confidence is one of {struggling, unsure, confident, mastered}. Do NOT assert the exact string value of topic. (3) For the loop's keep/discard signal, average scores over 3 runs rather than a single run. This is cheap and eliminates most variance.
- **[major] An unattended overnight loop hitting live LLM APIs has no cost or rate-limit guardrails. With autoagent running n=100 concurrency and an LLM extractor called per session (1940 sessions), a single loop iteration could issue thousands of API calls.**
  - Why: Bedrock and Anthropic both have TPM limits that will cause throttle errors that look like extractor failures. Cost could be substantial. A NEVER STOP loop (program.md:208) with no budget cap is a financial and quota risk.
  - Mitigation: Three guardrails: (1) An offline/stub evaluation tier using the hand-labeled fixtures with deterministic keyword classification as a fast pre-filter — run this first, only call the live LLM for the ~20% of sessions that score ambiguously on keywords. (2) A hard budget cap in the loop runner (e.g., max_cost_usd=5.00 per run, checked before each API call). (3) A max_iterations cap (e.g., 20 loops) in addition to NEVER STOP to prevent runaway.
- **[minor] Playwright tests cannot assert 'correct agent output' for non-deterministic prose. The user's stated goal of 'Playwright full-UX suite' conflates two incompatible testing targets.**
  - Why: Playwright is the right tool for asserting that the UI renders what the DB contains (e.g., 'when study_progress has a struggling row for outer joins, the Generate panel dropdown shows outer joins'). It is the wrong tool for asserting that the LLM extractor correctly identified a struggle in a specific transcript. Mixing these produces a fragile test that fails on UI changes unrelated to extractor quality.
  - Mitigation: Draw a clean boundary: Playwright tests assert UI behaviour given known DB state (seed DB fixture, render page, assert dropdown item). Unit/integration tests assert extractor behaviour given raw session transcript. The extractor's output is a structured record written to study_progress — assert THAT record was written with non-empty fields and valid confidence value. These tests are fully deterministic and do not require Playwright.
- **[minor] The session-type classifier (classifier.py) and the proposed struggle extractor solve DIFFERENT problems but share vocabulary. The classifier categorises session TYPE (learning vs debugging). The extractor must identify struggling TOPICS within a session. Conflating them will produce a loop that optimises session-type accuracy instead of per-topic struggle extraction.**
  - Why: A session typed as 'learning' with high confidence does not mean the user struggled with any specific topic — it just means they were asking questions. The ground-truth for the classifier tests (test_classifier.py:113-186) uses keyword-stuffed synthetic strings that would score perfectly on any reasonable classifier. These are not valid test cases for an LLM extractor that must read real conversational prose and extract specific topics.
  - Mitigation: Keep classifier.py as-is for session-type detection. Build the LLM extractor as a separate pipeline that reads raw message content (not classifier output) and produces structured {topic, concept, confidence} rows. The two pipelines should not share test cases or evaluation data.

### Angle: Evaluation / ground-truth strategy for the LLM-based struggle-extractor — covering dataset shape, label sourcing, train/held-out split, metrics+thresholds, and the deterministic pipeline gate.

- **[minor] Golden set is tiny and biased toward one person's vocabulary**
  - Why: The only real study Q&A content is from ~10-15 sessions, all from the same learner (Andy). The extractor could overfit to his phrasing ('socratic', 'AuDHD', 'SUPER helpful') and fail on any other user or topic framing.
  - Mitigation: Label sessions from all distinct topic domains (Python/OOP, AWS/SageMaker, data engineering, graphrag) to force topic diversity. Document the vocab bias as a known limitation in the eval README. For a single-user tool this is acceptable initially.
- **[major] Most sessions are build/tool-use (claude_code subagents), not study conversations — they will generate false-positive struggles if the extractor is run on all sessions indiscriminately**
  - Why: The ABC/Protocol session itself contains 60+ messages debugging a Python script (FTS trigger conflict). The extractor may extract 'sqlite3 FTS triggers', 'PRAGMA foreign_keys', 'Typer ArgumentInfo' as struggles, which are debugging episodes, not study struggles.
  - Mitigation: The extractor input MUST be pre-filtered: only process sessions where source=kiro_cli OR where the session project_path matches a study project. Add a session_type classifier upstream: if >50% of messages are tool_use/tool_result roles, skip. This pre-filter is part of the pipeline contract, not the extractor prompt.
- **[major] Confidence threshold on held-out set is unstable with N<20 samples**
  - Why: With only 10-15 golden sessions, F1 on topic detection has high variance. A single mislabel or LLM output variation at temperature 0 can swing F1 by 0.1+, making the gate unreliable for binary pass/fail.
  - Mitigation: Use a lower F1 threshold (>=0.60) initially and tighten it as the labeled set grows. Separately track precision (false positives are costly — they push junk into the study dashboard) and recall (false negatives just mean missed signal). Gate on precision >= 0.70 first.
- **[major] LLM extractor at temperature=0 is not fully deterministic across model versions or prompt changes**
  - Why: Claude may return slightly different topic normalizations ('ABC vs Protocol' vs 'abstract base class vs protocol') across runs, breaking exact-string assertions and causing flaky CI.
  - Mitigation: Never assert on raw LLM output strings. Assert only on normalized topic set overlap (lowercase, strip punctuation, Jaccard >= threshold). Store canonical topic names in a controlled vocabulary file that the extractor prompt includes as a reference.
- **[blocker] No baseline stub extractor exists yet — the plumbing test and quality eval are conflated**
  - Why: If the pipeline test (does record_progress get called with the right schema shape?) and the quality test (does the LLM find the right topics?) are run together, a DB schema error will fail the quality gate and make it look like an LLM failure, and vice versa.
  - Mitigation: Implement a STUB extractor (described in recommendations) before touching the LLM. The stub always returns a fixed hardcoded output. Run all plumbing tests against the stub first. Only switch to the real LLM extractor for the quality eval tier.
- **[blocker] label sourcing requires at least one human labeling pass — the 'no human in the loop overnight' goal cannot be 100% achieved on first run**
  - Why: The loop can only improve what it can measure. Without at least 10-15 hand-labeled (session_id, expected_topics, expected_confidence) rows, the eval has no ground truth and the autoagent loop is measuring noise.
  - Mitigation: This is unavoidable. Budget a single 30-minute labeling pass (described in recommendations). After that initial pass, the loop can be fully automated: generate new labels from near-unanimous LLM agreement on unlabeled sessions as a weak supervision strategy.

### Angle: Map the full test surface the handoff must specify: Playwright e2e UX + the per-harness session-DB-processing command.

- **[major] The LLM-based struggle extractor does not exist yet — only a keyword session classifier (classifier.py) and the log_topic MCP tool (uncommitted). There is nothing to test for 'periodic LLM extraction' because the module is not built.**
  - Why: The handoff will spec tests for a non-existent module. If the test spec is written against an assumed API that differs from what gets built, the fanout agents will fail.
  - Mitigation: Handoff must first spec the extractor's Python API (function signature, inputs, outputs), then spec the tests against that contract. Use a placeholder interface: extract_struggles(db_path: Path, session_ids: list[str]) -> list[ProgressRow]. Tests written against the interface will guide the builder agent.
- **[major] Interactive agent commands (Claude /slash, Kiro skill, Gemini @command) cannot be invoked headlessly in a test runner. The harness requires a live interactive session.**
  - Why: The user's stated goal was 'remove the human from the loop' with automated testing. If the only test surface is the interactive command, the test suite cannot run in CI.
  - Mitigation: Test the extractor core function directly with pytest (pure Python, no agent). Add a thin smoke test that the CLI subcommand is registered (typer app --help includes the subcommand name) and exits cleanly with a tmp db. This gives two-layer coverage: unit correctness + CLI wiring. The agent slash/skill command is a thin wrapper calling the CLI; its existence can be asserted by checking the command file exists (file presence test), not by exercising it.
- **[major] Playwright assert on struggling topics dropdown content is only deterministic with route-stubbing. With a real server + real DB, the dropdown content depends on what's in the user's live sessions.db, making the assertion non-reproducible.**
  - Why: A test that passes on the developer's machine because they happen to have struggling topics in their DB is not a test — it's a coincidence.
  - Mitigation: The real-server variant of the e2e test must use a tmp config pointing to a tmp sessions.db seeded in the test fixture (same pattern as stub_config in content gen e2e). The route-stub variant is simpler and faster for DOM-structure assertions. Both are needed: stub for the dropdown shape, real-server for the full API → DB → UI chain.
- **[minor] The Generate panel's scope_kind='topic_struggles' fetch fires on scope_kind change (index.html:1384), but Alpine state initialization sets strugglingTopics=[] (index.html:1301, 1371). If the radio is not clicked in the test, the fetch never fires and the dropdown stays empty — a test that clicks the radio but doesn't wait for the async fetch will give a false-negative.**
  - Why: Timing issue: page.route() stubs are synchronous but Alpine fetch is async. The test must wait_for_function that strugglingTopics.length > 0 before asserting option values.
  - Mitigation: After clicking the 'Topic I'm struggling on' radio, use page.wait_for_function('() => window.Alpine.$data(document.querySelector(...)).strugglingTopics.length > 0', timeout=3000). Pattern is identical to the wait_for_function calls in test_web_content_gen_e2e.py:321-328.

### Angle: Design for an autoagent-derivative hill-climber that iteratively improves the session-to-study_progress extractor prompt/logic using a precision/recall/F1 score against held-out golden labels.

- **[major] Held-out set Goodharting: with a small golden set the meta-agent can overfit the prompt to the specific phrasings in the held-out labels rather than learning genuine struggle detection**
  - Why: The whole point of the held-out gate is to detect overfitting — if the gate itself has too few examples (< ~30 sessions) it becomes another thing to overfit against
  - Mitigation: Enforce a minimum held-out size of 25 sessions; require F1_held_out improvement of at least 0.03 over baseline before 'keep'; add a third split (test set, never seen during loop) used only for final reporting
- **[major] Token budget runaway: the meta-agent calls the LLM twice per iteration (once to mutate the prompt, once to run eval over N training sessions), and N could be large**
  - Why: At 1940 study_sessions in the DB, running extraction on all training examples per iteration could cost $5-20 per run; overnight loops multiply fast
  - Mitigation: Cap eval batch at 50 training sessions per iteration (stratified sample); set MAX_ITERATIONS=20 and BUDGET_USD=5.00 hard stops; log cost_usd per run in results.tsv and abort loop when cumulative cost exceeds budget
- **[major] Golden label quality: the Angle 2 labelling process produces the ground truth, but if those labels themselves were produced by an LLM they inherit that model's biases — the hill-climber optimises toward a potentially flawed oracle**
  - Why: The score function is only as good as its labels; if labels say 'Python closures' is not a struggle when the transcript clearly shows confusion, the extractor is penalised for being right
  - Mitigation: Require human spot-check of at least 20 golden labels before starting the loop; document labelling criteria explicitly (struggle = user asks to re-explain, expresses confusion, gets correction from assistant 2+ times); treat F1 improvement as relative signal not absolute truth
- **[minor] Determinism gap: LLM extraction is non-deterministic even at temperature=0 across model versions; a 'keep' run may not reproduce when re-run on the same data**
  - Why: The keep/discard decision is based on a single eval run; variance in LLM output could accept a bad prompt or discard a good one
  - Mitigation: Run eval twice per candidate prompt (2 passes, same sessions, temperature=0); only keep if both runs show improvement; use the mean F1 as the score in results.tsv
- **[minor] Prompt mutation strategy is underspecified: if the meta-agent mutates randomly it wastes budget; if it only refines the current prompt it gets stuck in local optima**
  - Why: autoagent escapes local optima by analysing failure trajectories; the StudyLoop derivative needs an analogous 'failure analysis' step
  - Mitigation: After each eval run, collect false-negative examples (missed struggles) and false-positive examples (over-labelled non-struggles) and include a 5-example sample in the mutation prompt. The meta-agent is told: 'these are your specific failure modes — mutate to fix them'
- **[blocker] Autonomy risk: 'NEVER STOP' from autoagent's program.md is dangerous when the eval target is a live production DB**
  - Why: The derivative reads the golden labels and sessions DB but must NEVER write to the production DB during iteration — only the final accepted extractor writes to study_progress
  - Mitigation: Eval loop operates exclusively on in-memory golden labels and a temp SQLite copy; the production DB write happens only on explicit human sign-off of the final prompt, not automatically
